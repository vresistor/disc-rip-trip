# Audio audit, 20 November 2026

Done again from scratch after the week's changes: data riding on items, Rip
taking the offset from the disc, encoders losing their cover, tag and verify
switches, Cue moved after the Library, and the Lyrics file step.

**Verdict: archive quality, yes.** All 13 tracks of a real disc match
AccurateRip. I computed the CRCs myself from the filed FLACs (decoded with
libFLAC, not our ffmpeg) and they match both cyanrip and the database. The
tracks join with no gaps, and every lossless file decodes to exactly what was
read. Nothing in the chain touches the samples. I found five bugs and fixed
them. None of them changed the audio in this rip. One of them (the WAV
parsing in Combine) could corrupt a combined track. Two others are tagging
bugs, which every file filed before this fix carries.

## A. Code audit

Path traced: Drive → Audio CD → lookups → Choose → Cover art → Rip
(`real/mod.rs`, `cyanrip.rs`, `offset.rs`) → encoders (`encode.rs`) → Folder
(`mod.rs` `Place`) → Cue (`cue.rs`), and also ReplayGain (`replaygain.rs`),
Lyrics file (`lyrics.rs`) and the engine's join (`engine/src/run.rs`).

**What holds**

- **Offset.** Drive puts the drive-scoped offset on the disc item
  (`mod.rs:146-149`). Rip reads it from there and refuses to run without it
  (`mod.rs:554-555`). Every read uses the same `opts` closure, so the first
  read, careful reads, retries, *Slowly* and Combine all pass `-s <offset>`
  (`cyanrip.rs:139`). The join merges each branch's context and de-duplicates
  facts, so the offset survives the lookup branches once. The real run found
  +103 through `find_missing` ("AccurateRip, 528 agree"), and cyanrip logged
  `Offset: +103 samples` for every track.
- **AccurateRip.** `-A` is passed only when there is no offset, which Rip
  never allows, so every read is checked. A verdict needs a line that says
  "accurately ripped" (`cyanrip.rs:177`). Mismatch and not-in-database both
  lead to a careful re-read. cyanrip handles the first/last-track skips, and
  that was proven independently (below).
- **Majority vote** (`combine`). Ties go to the earliest read, and a frame
  with no majority is counted as unsettled. Tested.
- **Sample format.** No `-af`, `-ar`, `-sample_fmt` or dithering anywhere on
  the encode path (a test now asserts this). ReplayGain only measures
  (`ebur128` into `-f null`) and writes with `-map 0 -c copy`. A remux of a V0
  MP3 keeps the LAME delay/padding fields (checked: `0x2404ec` before and
  after). Lossy formats change the audio by design. Opus always runs at 48 kHz.
- **Settings to flags.** FLAC `-compression_level N`. MP3 `-q:a 0`,
  `-joint_stereo 1`, `-id3v2_version 3|4` and `-write_id3v1`; CBR uses `-b:a`,
  ABR `-abr 1`. Opus `-b:a`, `-vbr on|constrained|off`, `-compression_level`,
  `-application`. AAC `-b:a`. Vorbis `-q:a`. ALAC `alac`. WavPack levels 0–3.
  WAV `pcm_s16le`. All checked against `audio_args` and the existing tests.
- **FLAC verify** (`encode.rs`, end of `encode`). It compares the MD5 of the
  PCM decoded from the source WAV (the rip, or the combined file) with the
  MD5 of the PCM decoded from the new FLAC, both through `-map 0:a -c:a
  pcm_s16le -f md5`. A mismatch fails the track (`Bad`), and it is not filed.
- **Gapless.** One cyanrip process per track, with pregaps merged into the
  previous track (cyanrip's default). Track 1's pregap is dropped, so a hidden
  track one is not extracted. That is cyanrip's default and the 2026-11 review
  notes it, but `docs/audio-accuracy.md` doesn't say it.
- **Folder** (`mod.rs` `Place`). `tokio::fs::copy` to `<name>.<ext>.part`,
  then rename in the same directory: a byte copy, swapped in atomically. It
  never moves files.

**Findings**

| # | Severity | Where | Finding | Status |
|---|---|---|---|---|
| 1 | High (rare) | `mod.rs` `differences`, `combine` | The PCM was found by searching for the bytes `data`. cyanrip writes a LIST/INFO chunk (CD-Text title, album) before the data chunk, so a title like "Metadata" would make Combine read and write the samples shifted by a few bytes. The FLAC verify would pass, because it checks against the corrupted WAV. | **Fixed**: `wav_data` walks the RIFF chunks. Test `samples_are_found_by_their_chunk_not_by_the_word_data`. |
| 2 | Medium | `mod.rs` Combine | `while reads.files.len() < 3` looped for ever when a track never read: it held the drive and never stopped. | **Fixed**: at most 6 tries, then "read failed". Test `combine_stops_reading_a_track_that_never_reads`. |
| 3 | Medium | `encode.rs` | ffmpeg copied the rip WAV's own INFO tags into every output. Every file carried `comment/DESCRIPTION=cyanrip 0.9.3`. With no release chosen, `title=Unknown track` and `album=Unknown disc (XXXX)` would leak too. | **Fixed**: `-map_metadata -1` in the new `ffmpeg_args`. Test `only_the_tags_given_are_written_and_the_cover_is_the_front`. |
| 4 | Low | `encode.rs` `cover_args` | The cover was embedded as picture type 0 "Other" (FLAC PICTURE and MP3 APIC), not 3 "Front cover". | **Fixed**: `-metadata:s:v comment=Cover (front)`, checked with the bundled ffmpeg to give type 3 in FLAC and MP3. Same test. |
| 5 | Low | `mod.rs` retry loop | A *Read again* / *Slowly* read that matched AccurateRip was reported as "✓ two reads agree" and not counted as verified. | **Fixed**: `settled_note`. Test `a_careful_read_that_matches_accuraterip_counts_as_verified`. |
| 6 | Low | `cue.rs` `rip_log` | The rip log counted "✓ two reads agree" and "✓ combined" as *verified*. Rip counts only AccurateRip matches. | **Fixed**: uses `is_accurate`. Test `the_rip_log_counts_only_accuraterip_matches_as_verified`. |
| 7 | Low | `cli/src/main.rs` | `drt --auto` (or pressing Enter) set any unknown offset to +103 and never looked at AccurateRip's list. | **Fixed**: real drives look the offset up first, and with no answer the CLI stops. Test `a_real_drive_never_gets_a_guessed_offset`. |

**For the owner (debatable, not changed)**

- **De-emphasis is on** (no `-W`). On a pre-emphasis disc cyanrip changes the
  samples. For a strict archive, pass `-W` and mark the files instead.
- **Hidden track one** audio is dropped, and `docs/audio-accuracy.md` doesn't
  say so. There is no overread (`-O`), so the last 103 samples of the last
  track are silence. This is normal for this drive, and AccurateRip ignores
  them.
- **Combine votes with the fast first read** as well as the careful ones. Its
  "combined, N unsettled" verdict files the track as Ok.
- **Only FLAC is verified.** ALAC, WavPack and WAV are lossless too but go
  unchecked.
- **Tag conventions.** FLAC and Opus get `TRACKNUMBER=1/13` (players expect
  `TRACKNUMBER=1` with `TRACKTOTAL=13`). MP3 ISRC goes to `TXXX:isrc`, not
  `TSRC`. MusicBrainz IDs go to `TXXX:musicbrainz_albumid` and the like, where
  Picard uses `MusicBrainz Album Id` and a UFID frame. The MP3 Info tag is
  written by ffmpeg ("Lavc"), so the header doesn't record "V0".
- **Folder** overwrites an existing file of the same name without a word,
  and doesn't fsync before the rename.
- **The extra ffmpeg arguments** field can carry `-af` and the like into any
  encoder.
- **Two pressings.** At the drive's +103, AccurateRip's match has confidence 5.
  The same samples shifted by 18 frames match the confidence-43 entry on every
  track (below). The read is right either way. The ambiguity is in which
  pressing this is, as `judge_measurement` already says.

## B. A real rip, checked independently

Disc: Parquet Courts, *Wide Awake!* (Rough Trade RT0001CD), 13 tracks, in the
MATSHITA BD-MLT UJ240AS. Recipe: Drive → Audio CD → MusicBrainz + CD-Text →
Choose (auto-picked: the only release) → Cover art → Rip → FLAC 8 / MP3 V0 /
Opus 160 VBR → three Folders under `target/audit/lib` → Cue after the FLAC
folder. No Next disc step.

Setup: a temporary harness with the real registry (since deleted),
`XDG_CACHE_HOME`/`XDG_CONFIG_HOME` pointed into `target/audit`, and cyanrip and
ffmpeg run through the flatpak. Hard links of the work folder were kept as it
ran, so the WAVs and encoder outputs survived the clean-run tidy-up.
Independent tools: host `flac` 1.5.0, `metaflac`, host ffmpeg/ffprobe 8.1.3,
and my own Python/numpy AccurateRip script.

Result: 13/13 verified (✓ 5), first read at paranoia 0, no retries.

1. **FLAC integrity.** `flac -t` and `ffmpeg -v error … -f null -` are clean
   on all 13. For every track, the STREAMINFO MD5, the MD5 of the PCM decoded
   by libFLAC, and the MD5 of the rip WAV's data chunk are identical.
2. **AccurateRip.** Disc IDs from the TOC were `001468e3-00c611ce-cd09120d`.
   The CDDB ID matches the rip log. I fetched the dBAR (3 entries). The CRCs
   were computed from the FLACs decoded by libFLAC, skipping 5×588−1 frames at
   the start of track 1 and 5×588 at the end of track 13.

3. **Gapless.** Each track's frame count equals its TOC length × 588. The
   total is 102,430,188 frames, which equals (leadout − track 1) × 588. Track 1
   starts at LBA 0, so this disc has no hidden track.
4. **Formats** (ffprobe). FLAC: s16, 44.1 kHz, 2 ch, 16-bit. MP3: 44.1 kHz,
   2 ch. Opus: 48 kHz, 2 ch (inherent to Opus; pre-skip 312).
5. **MP3.** ID3v2.3 on all 13. Every one of the 88,937 frames is joint
   stereo. Frame bitrates range from 32 to 320 kbps, averaging 247–306 kbps
   per track: VBR, consistent with `-q:a 0`. The header can't show V0 (see
   above).
6. **Opus.** VBR, 142–167 kbps per track against 160 set. 2 channels.
7. **Tags and covers.** Title, artist, album and MusicBrainz track ID match
   the chosen release in all 39 files. The 1200 px cover is embedded in FLAC
   and MP3 and absent from Opus (by design). This rip predates fixes 3 and 4,
   so its files carry `comment=cyanrip 0.9.3` and picture type 0.
8. **Folder.** All 39 filed files are byte-identical (`cmp`) to the encoders'
   outputs.
9. **Tamper test** (copy of track 7):
   - One byte flipped: `flac -t` aborts. The app's verify command gives MD5
     `b32f…` against the rip's `3593…`, so the track would fail.
   - One sample changed and re-encoded into a valid FLAC: `flac -t` passes, as
     it must. The app's verify gives `7a72…`, which differs from the rip's.
     The independent AccurateRip CRC becomes `50D7767F`, confidence 0.
